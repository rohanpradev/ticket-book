## Additional standards research

Knip 6.42.1 was checked against the current package registry and integrated with the existing Vite+ configuration. [Knip’s Vite+ plugin](https://knip.dev/reference/plugins/vite-plus) discovers build inputs; subprocess crash fixtures are declared entry points. [TypeScript indexed access](https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html) and [exact optional properties](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html) expose absent-value assumptions. [Zod’s official parsing guidance](https://zod.dev/basics) informs the shared runtime contracts. [Bun audit](https://bun.com/docs/pm/cli/audit) checks the lockfile; it is a known-advisory check, not proof that dependencies are vulnerability-free. [GitHub’s secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use) informs full-SHA action pins and read-only CI permissions. Action hashes were resolved from the official repositories’ corresponding release tags.

## Bun 1.4.4 upgrade

The [Bun 1.4.4 release notes](https://bun.com/blog/bun-v1.4.4) informed the runtime and lockfile upgrade. The refreshed lockfile includes libc metadata for updated native dependencies, allowing Bun to select the matching Linux build. Frozen installs remain required in CI and Docker.

Keep using `bun run check` and `bun run format`: the former includes Vite+ policy, Knip, and unit tests, while formatting options live in `vite.config.ts`. Bun's new native formatter does not replace that configuration. Native type checking is also distinct from the full repository check. The release's Bun.SQL features do not apply to the existing postgres.js/Drizzle adapter. The Dockerfile already caches dependency installation separately from source changes, so an extra `bun pm fetch` layer is unnecessary here.

The container baseline uses PostgreSQL 18.6, Redis 8.10.2, and Nginx stable 1.30.6, verified against the [official PostgreSQL image metadata](https://github.com/docker-library/official-images/blob/master/library/postgres), [Redis image metadata](https://github.com/docker-library/official-images/blob/master/library/redis), and [Nginx image metadata](https://github.com/docker-library/official-images/blob/master/library/nginx). PostgreSQL and Redis retain their existing major versions and persistent volumes. No schema migration or environment regeneration is required. The [Node release index](https://nodejs.org/dist/index.json) supplies the optional CLI runtime pin; [CodeQL action v4.39.1](https://github.com/github/codeql-action/releases/tag/v4.39.1) is pinned to its verified commit.

Upgrade verification on Bun 1.4.4:

- Frozen offline installation, `bun run check`, `bun run build`, and `bun run audit` passed; the audit reported no known vulnerabilities across 255 packages. The registry reported no outdated direct dependencies.
- All 14 unit tests and 29 PostgreSQL/Redis integration tests passed. The new HTTP-provider regression withholds a response after committing its effect, exercises the actual three-second deadline, and verifies a durable retry with the same event ID, a fresh claim token, and unchanged confirmation/inventory state.
- The complete verification sequence also passed in a fresh Linux x64 Bun 1.4.4 container, using only tracked source files, no local `.env` or `node_modules`, and separate disposable PostgreSQL/Redis services. This included frozen installation, audit, checks, build, database preparation, integration tests, and benchmark. Workflow expressions and shell steps passed Actionlint.
- The Linux production image built with frozen dependencies. Its API reported PostgreSQL and Redis ready, served the production page, and exited with code 0 after SIGTERM. Nginx 1.30.6 accepted the existing gateway configuration. Compose and workflow YAML validated locally; hosted CI and CodeQL provide additional verification when changes are pushed or submitted as a pull request.
- Sandbox discovery, admission, seat selection, reservation, confirmation, and ticket navigation were checked at 1280×720 and 390×844. These are browser-local flows; server contracts and correctness were checked separately by the integration suite.
- The isolated benchmark was regenerated on the pinned services. All phases passed: 100 competing requests produced one owner; 40 cross-replica replays returned the same order; duplicate checkout left 12 confirmed orders and 12 delivered events with consistent inventory. See [the measured report](benchmarks/latest.json) for latency distributions and workload details. Local runs varied; this is not a controlled before/after performance comparison or a production capacity claim.
